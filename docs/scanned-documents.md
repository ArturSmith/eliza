# Scanned documents

Open **Eliza AI** (`/ai`) to upload a JPEG, PNG, WebP, or PDF up to 8 MB, Attach the file in the chat composer and send it. The backend sends the original image/PDF to the OpenAI Responses API using strict structured output; `OPENAI_API_KEY` stays on the server. The model is `OPENAI_DOCUMENT_MODEL` when set, otherwise `OPENAI_MODEL`, otherwise `gpt-4o-mini`.

The result appears directly in the chat as a draft, with the original file above its editable digital reconstruction. It can show parties, fields, paragraphs, one or more tables, annotations, printed totals, and warnings; documents without tables remain valid. The user can edit fields and table rows in chat, then explicitly save the digital document. The original extraction remains unchanged. Printed totals are never overwritten by calculated row sums. Use **Digital documents** in the chat composer to search and reopen drafts or saved versions without another model call. **Export PDF** opens the browser print dialog, where the digital reconstruction can be saved as a PDF; use a Unicode-capable browser font for Cyrillic.

The original bytes and the extracted/edited JSON are stored in PostgreSQL by migration `0021_scanned_documents.sql`; migration `0023_scanned_document_drafts.sql` distinguishes drafts from saved digital documents. The original file endpoint and document endpoints require an authenticated user with purchasing read access. Scanning and saving require purchasing write access. The app caps scans at five per minute per store. Files are store-scoped and included in database backups. If scans become numerous or large, move original files to private object storage and keep only references in PostgreSQL.

Digital scanned documents are separate from purchase orders. Scanning or saving a document does not create a supplier, product, purchase order, or inventory movement. Connecting a saved digital invoice to purchasing is future work.

## Dense tables and accuracy

The uploaded file remains unchanged in PostgreSQL. The browser does not resize or compress it. For images, the API checks orientation with Sharp. If an EXIF rotation is needed, it makes a correctly oriented analysis copy while retaining the original bytes. Images at least 800 pixels tall and PDFs at least 100 KB get a separate layout inspection to estimate the printed row range. The full document is then reconstructed with `detail: high`; PDFs explicitly use `detail: high` for page images. When a single table has at least 16 numbered rows, the API additionally reads four overlapping, full-resolution vertical image crops (or numbered row ranges for PDFs), then merges those readings by printed row number. Different readings of the same row remain visible as review warnings. This uses more model calls and API credits than a short scan.

The document model defaults to `gpt-4o-mini` unless `OPENAI_DOCUMENT_MODEL` or `OPENAI_MODEL` is set. A whole image at high detail may be internally resized by that model; smaller full-resolution crops reduce that risk. The response limit is 16,000 output tokens for the full reconstruction and 5,000 for each table section. Incomplete model responses are rejected without saving a document.

For numbered tables, validation compares the printed first/last row and expected count with extracted row numbers. Missing or duplicate numbers, uncertain cells, and conflicting section readings trigger a **Review required** state. A 25-of-31 extraction is labeled incomplete; its sum is a partial sum, not a confirmed arithmetic discrepancy. A document with missing or duplicate rows remains available for correction and review. Editing and history remain available. Printed prices and quantities are preserved as separate source cells; unreadable cells may be `null`, and the app does not default a missing quantity to one.

Run `pnpm build`, `pnpm db:migrate`, then `pnpm dev`. Set `OPENAI_API_KEY` on the backend. To verify without calling OpenAI, run `pnpm exec vitest run tests/scanned-document.unit.test.ts` and `pnpm exec vitest run --config vitest.integration.config.ts tests/scanned-documents.integration.test.ts`; the integration test stubs the provider. Run `pnpm exec playwright test tests/e2e/scanned-documents.spec.ts` for the browser flow. For a live smoke test, scan a real image/PDF and compare every field and row to its original before using the result.

Limits: model transcription may be wrong, especially for low-quality scans, handwriting, or long PDFs. The output schema supports up to 100 pages, 30 tables, and 500 rows per table, but long documents can exceed the model response limit. PDF export uses the browser print dialog rather than server-side PDF generation. The reconstruction keeps logical document structure, not the original page geometry.
