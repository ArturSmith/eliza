# Customer App integration

The separate `Eliza Customer App` project has its own mobile web UI, HTTP API and PostgreSQL database for customer profiles and authentication. The platform owns loyalty programs, membership references, campaigns, redemption authorizations and the append-only bonus ledger. No customer PII is copied into platform membership records. The customer service never connects to the platform database.

Deploy the platform's migration `0060_customer_loyalty.sql` and `0061_loyalty_collect_spend.sql`, plus all subsequent migrations through `0065_rotating_loyalty_qr.sql` using the existing migration flow. Configure a random server-only `CUSTOMER_APP_SERVICE_TOKEN` of at least 32 characters on both API services. The integration namespace `/api/integrations/customer/v1/` authenticates that token independently of browser cookie/Origin protection; all existing management/POS routes keep their original protection. With no token configured, integration access is closed. Desktop integration remains disabled.

Owner and Manager roles receive `loyalty.manage`. Open **Loyalty program** to configure rewards. Shops appear in the loyalty join list only when the program is enabled.

Campaigns are optional cards for actual promotions. In **Promotions**, select products/categories, set the discount and schedule, then choose **Create a campaign card for the customer app** and fill its title/details. Publish immediately or keep the card as a draft. Existing promotions have **Create campaign card** / **Edit campaign** actions. Management uses `promotions.manage`, not `loyalty.manage`. Promotion creation and its optional card are saved in one transaction. Card updates use optimistic versions and never modify prices.

Published cards are available to all signed-in customers, without loyalty membership or an enabled program. Cards inherit the promotion's targets, discount and dates; cancellation, disabling or expiry automatically removes them from the feed. Offers without an end remain visible while the promotion is active. The customer API loads `/api/integrations/customer/v1/campaigns`; the former customer-specific campaign read route remains an alias for older servers. Legacy standalone records in `loyalty_campaigns` are preserved but are no longer displayed. Create linked cards in Promotions rather than automatically inventing promotions or discounts for old announcements.

At checkout, scan the customer's live membership QR, which refreshes every 30 seconds. The platform rejects expired or permanent codes. Scanning returns a separate five-minute authorization bound to the cashier and register, consumed with one sale. A repeat scan on the same checkout is safe during the display window; another checkout is rejected. The POS uses the returned authorization, never the raw display code, for payment. The cashier sees the current balance and asks the customer to choose **Collect** or **Spend**. Collect earns bonuses without spending any. Spend uses the smaller of the positive balance and purchase total, earns no new bonuses, and permits a fully bonus-paid purchase. A customer with 100 points buying a product for 50 spends 50 points, pays no cash and retains 50 points. Any amount not covered by the balance is paid by cash/card. There is no percentage cap or second customer authorization QR in this flow.

The platform rechecks/locks the membership in the sale transaction. Resolving a card never changes its balance, and safe request retries cannot debit it twice. Refunds restore the original spent bonuses and reverse original earned bonuses with cumulative rounding, including partial returns and purchases paid entirely with points. Negative balances after returning previously rewarded purchases are visible and cannot be spent. Historical receipt snapshots stay unchanged.

Legacy one-time authorization endpoints/codes remain supported for older clients; the Customer App no longer generates them. The old `redeem_percent` database column is retained for compatibility at 100%. Migration 0061 changes existing programs and advances their optimistic versions without altering past sales or balances.

Version 1 has no tiers, point expiration, category exclusions, email verification, recovery or message delivery. Email verification/recovery and customer privacy information remain launch work. No production database reset is necessary. Deploy the platform before the customer service, keep their databases and `APP_ORIGIN` values distinct, and back up both databases.

The independent project's README contains the Railway variables and setup steps; its API.md documents all customer/server integration endpoints. Its integration and browser suites use two disposable local databases and verify live communication with the platform. They do not modify production or existing local app data.

Deploy the platform and its migrations before the Customer App update. The existing server-only `CUSTOMER_APP_SERVICE_TOKEN` also derives checkout authorizations; no new credential is needed. `loyalty_qr_tokens` stores token hashes and expiry/binding information. The authenticated Customer API GET `/api/v1/memberships/:id/qr` proxies a platform-owned issuance operation. Old permanent membership values remain for history but are no longer accepted; legacy redemption issuance returns 410. Exact retries of a completed sale return the recorded receipt even after expiry. Refund allocation logic is unchanged. The app hides expired QR codes if refresh fails, and refreshes on foreground resume. Screenshot reuse is limited to 30 seconds; live forwarding within that period remains possible.

Membership reads also return `totalSaved`: the lifetime value of redeemed points at that membership's shop, minus points restored on refunds. It is calculated from the complete platform ledger in the same aggregate as the balance, independently of the activity feed's 100-entry limit. The customer home shows this amount in the shop currency under the QR and replaces the visual points meter with the program name, description, current balance, and earning/spending/refund conditions. No new database migration is required for this presentation and aggregate.
