# Архитектура цен и скидок V1: решение для Eliza

Статус: проектное решение, **не описание уже реализованной V1**. Основано на сравнении текущего кода с документом «SUPERMARKET PLATFORM — DISCOUNTS V1». Фокус: (1) уценка отдельных единиц товара (*unit markdown*), (2) акции на товары и категории (*product/category promotions*). Купоны, лояльность, BOGO, сложное совмещение и динамическое ценообразование в V1 не входят.

## Решение в одном абзаце

Обычная цена остаётся у исходного `Product`. Акция — самостоятельное правило, которое в момент сканирования обычного штрихкода вычисляет цену для товара или категории. Уценка единицы — отдельный одноразовый токен с собственным непрозрачным штрихкодом и **зафиксированной** ценой; токен указывает на исходный товар и конкретную учётную партию. Уценка не создаёт «товар-клон» и не уменьшает физический остаток при печати этикетки. Однако она резервирует право на одну единицу выбранной партии, чтобы обычная продажа не списала её себестоимость раньше уценённой продажи. Авторитетный расчёт цены и окончательная проверка токена выполняются на сервере в транзакции продажи. `SaleItem` сохраняет фактическую цену, источник цены и точную себестоимость партии.

## Сопоставление с текущей реализацией

| Область | Сейчас | Целевая V1 | Вывод |
|---|---|---|---|
| Обычная цена | `products.price`; цену можно менять в Edit product. | Остаётся базовой ценой товара. | Сохранить. |
| Скидка на весь товар | `products.price` заменяется скидочной ценой; прежняя хранится в `regular_price`, `price_kind='discount_all'`. | Продуктовая акция с фиксированной ценой либо процентом; базовая цена не меняется. | Перенести существующие активные скидки в акции, убрать две конкурирующие истины о цене. |
| Скидка на категорию | Отсутствует. Категория — свободный текст `products.category`. | Динамическая акция по стабильному `category_id`. | Сначала нормализовать категории; не расширять свободный текст как идентификатор. |
| Уценка N единиц | На каждую задействованную партию создаётся связанный `Product`, общий для неё штрихкод и перенесённый остаток. | Один `Markdown` и N уникальных `MarkdownUnit`/штрихкодов, по одному на физическую единицу. | Перейти от учётных товаров-клонов к одноразовым токенам. |
| Партии и себестоимость | Существуют `stock_batches`, `sale_batch_allocations`; стоимость конкретной партии сохраняется. | Каждый токен закреплён за партией; при продаже списывается именно она. | **Не** откладывать интеграцию с партиями: она уже есть и критична для маржи. |
| Учёт количества | Создание уценки переносит количество между двумя товарами через `movements`. | Создание уценки не меняет физический остаток и не создаёт движение продажи; продажа уменьшает остаток один раз. | Добавить логический резерв по партии, отдельный от физического остатка. |
| Повторное сканирование | Общий штрихкод можно использовать, пока есть остаток группы. | Один токен успешно продаётся только один раз. | Атомарное погашение токена при завершении продажи. |
| Историческая цена | Чек и `sale_items` хранят цену продажи; себестоимость фиксируется через списание партии. | Дополнительно явно сохраняются источник цены и ID акции/уценки. | Исторические суммы сохранить; добавить объяснимость скидки. |
| Печать | Несколько одинаковых этикеток на группу партии; повторная печать доступна. | Один уникальный код на этикетку; замена аннулирует старый токен. | Нельзя гарантировать защиту от *физического копирования* кода, но можно гарантировать не более одной успешной продажи. |

Текущие отправные точки в коде: `apps/api/src/price-actions.ts`, `apps/api/src/checkout.ts`, `apps/api/src/stock-batches.ts`, `apps/api/src/analytics.ts`, `apps/web/src/price-actions.tsx`, миграция `0045_product_price_actions.sql`.

## Модель данных

### Категории

Добавить `categories(id, store_id, name, ...)` и `products.category_id` с внешним ключом. Перенести существующие текстовые категории в строки этой таблицы, объединив только очевидные совпадения внутри магазина. Текст `products.category` временно оставить для совместимости API и исторического отображения; новый источник идентичности — `category_id`. Переименование категории не должно разрывать действие акции. Категория, созданная в ходе активной акции, получает скидку динамически, если добавлена как цель этой акции.

### Акции

`promotions`: `id`, `store_id`, `name`, `discount_type` (`PERCENTAGE` или `FIXED_PRICE`), `discount_value`, `starts_at`, `ends_at`, `enabled`, `cancelled_at`, `created_by`, `created_at`, `updated_at`. Хранить время как `timestamptz`; введённое менеджером местное время переводить в UTC с использованием часового пояса магазина. Фактическая применимость вычисляется из интервала `[starts_at, ends_at)` и признаков включения/отмены. Фоновый cron для переключения «ACTIVE» не нужен.

Для целей лучше использовать две таблицы с настоящими FK: `promotion_products(promotion_id, product_id)` и `promotion_categories(promotion_id, category_id)`. Полиморфная пара `target_type/target_id` выглядит компактнее, но не позволяет обычным FK проверить обе разновидности цели. Уникальные ограничения не допускают повторов внутри акции; связи и запросы всегда ограничены `store_id`.

Категорийная акция с `FIXED_PRICE` применяется только там, где фиксированная цена **ниже** текущей базовой цены товара: акция не должна случайно повысить цену дешёвого товара.

### Уценка единиц

`markdowns`: `id`, `store_id`, `product_id`, `quantity`, `reason`, `base_unit_price`, `final_unit_price`, `valid_from`, `valid_until`, `cancelled_at`, `created_by`, `created_at`. В V1 интерфейс может принимать итоговую цену, как сейчас; процент — лишь способ *рассчитать предлагаемую итоговую цену*, которая фиксируется при создании. Причина уценки обязательна и имеет расширяемый код (`EXPIRING_SOON`, `DAMAGED_PACKAGING`, `CLEARANCE`, `OVERSTOCK`, `OTHER`).

`markdown_units`: `id`, `store_id`, `markdown_id`, `product_id`, `batch_id`, `barcode` (уникальный непрозрачный код), `status`, `printed_at` (информационный признак, не доказательство фактической печати), `sold_at`, `sale_item_id`, `cancelled_at`, `replacement_for_id`. На каждую из N выбранных единиц создаётся ровно одна строка. Срок годности берётся из её партии для этикетки; время действия уценки ограничивается `valid_until` и доступностью партии. Токен не содержит цену: сканирование всегда обращается к БД.

При продаже токен не удаляется. История статусов и связи с чеком остаётся доступной. Уникальный индекс на `barcode` и уникальная связь проданного токена с `sale_item_id` дополняют транзакционную проверку состояния.

### Снимок цены продажи

Уже существующие `sales.receipt`, `sale_items.price`, `sale_items.total`, `sale_items.cost_total` и `sale_batch_allocations` сохраняются. Добавить к `sale_items` минимальные поля: `base_unit_price`, `pricing_source` (`REGULAR`, `PROMOTION`, `MARKDOWN`), `promotion_id` и `markdown_unit_id` (взаимоисключающие), `discount_total`. Markdown-строка имеет количество **ровно 1**, что позволяет однозначно связать её с одним токеном. Если касса объединяет одинаковые обычные товары в одну строку, это не меняет правило для markdown.

Исторический чек хранит отображаемое название акции/причину и рассчитанные суммы как снимок. Позднейшие изменения названия акции, цены товара или уценки не меняют уже завершённые продажи. `sale_item_price_adjustments` отдельной таблицей для V1 не требуется: ровно один источник скидки применяется к строке.

## Логический резерв и фактический склад

Документ-образец прав в главном: создание уценки **не должно уменьшать физический остаток**. Но его предложение совсем не резервировать партию плохо сочетается с нашей точной себестоимостью. Если обычная продажа по FEFO спишет все три йогурта из партии, к которой привязаны три уценённые этикетки, сервер позднее не сможет корректно продать эти этикетки с себестоимостью той партии.

Поэтому рекомендация — **логический резерв без складского движения**:

- `physical_on_hand(batch) = stock_batches.quantity`;
- `reserved_for_markdown(batch) = число неиспользованных действующих токенов этой партии`;
- `normal_barcode_available(batch) = physical_on_hand - reserved_for_markdown`;
- при создании N токенов проверять свободный остаток и закреплять их за партиями, автоматически по ближайшему сроку годности;
- обычная продажа списывает только свободное количество, уценённая — ровно указанную токеном партию;
- при продаже уценки в **одной транзакции** уменьшаются физический остаток и резерв (токен становится `SOLD`), создаётся обычное движение `sale`;
- отмена/истечение уценки освобождает резерв, но не создаёт движение физического товара. Просроченная сама по себе партия всё равно недоступна к продаже.

Таким образом, магазин по-прежнему имеет 10 физических йогуртов после печати трёх этикеток, но обычным штрихкодом доступно 7, а три — по своим кодам. Это сознательное отличие от предложения «разрешить продать все 10 обычным кодом»: оно защищает точную себестоимость, остаток и выпущенные этикетки. Менеджер не выбирает партию вручную; система показывает, какие сроки годности она выбрала, чтобы этикетки были наклеены на правильные упаковки.

Резерв должен считаться/обновляться транзакционно под блокировкой соответствующих партий. Для скорости можно хранить счётчик на партии, но тогда БД и сервис обязаны поддерживать инвариант `0 <= reserved <= quantity`; без измеренной необходимости V1 может начать с индексируемых строк токенов и блокировки партии.

## Серверное разрешение цены

Один модуль `PricingService` внутри существующего NestJS-монолита, **не отдельный сетевой сервис**, отвечает за предварительный ответ кассе и окончательный расчёт при продаже. Он принимает `store_id`, исходный `product_id`, контекст отсканированного кода, количество и момент времени; возвращает базовую и итоговую цену, источник, ID победившей акции или токена, включённый налог и понятное обозначение для UI. Расчёт денег использует имеющиеся decimal-string/scaled-BigInt функции, без `number` для суммы и без второго алгоритма округления в React.

Порядок V1:

1. Если введён markdown-код, найти токен по индексированному коду и `store_id`. Проверить товар, статус, время действия и партию. **Вернуть зафиксированную при создании цену.** Никакие акции сверху не применять. Неверный/использованный/отменённый код даёт явную ошибку, не запасной поиск обычного товара.
2. Если введён обычный штрихкод, взять текущую базовую цену `products.price`, найти действующие акции по самому товару и `category_id`, вычислить кандидатов и выбрать **минимальную итоговую цену**. Совмещения двух акций нет. При равенстве победителя выбирать детерминированно: сначала цель `PRODUCT`, затем стабильный `promotion_id`. Это влияет на объяснение и отчёт, а не на платёж.
3. Если подходящих акций нет, вернуть обычную цену.

Процентная акция пересчитывается от **текущей** базовой цены; фиксированная хранит заданную итоговую цену. Итоговая цена для клиента включает налог, как и существующая `products.price`; налог извлекается из фактически оплаченной суммы по существующему алгоритму. Сервер не доверяет цене, присланной POS. Интерфейс показывает предварительную цену, но при оплате сервер **повторно** разрешает её в транзакции. Если цена, акция или токен изменились после добавления в корзину, продажа отклоняется с требованием обновить корзину — по аналогии с текущей проверкой `expectedPrice`/`expectedTaxRate`.

Для V1 достаточно индексированных запросов по магазину, состоянию и целям. Кэш цен не вводить до измерения проблем производительности: границы действия акции и отмена делают ошибочный кэш особенно опасным.

## Жизненный цикл и безопасность

**Акция:** черновик → включена/запланирована → применима в своём интервале → завершилась по времени или отменена. «Активна сейчас» — производное состояние, не поле, которое cron обязан вовремя поменять. Отмена действует только на будущие продажи; завершённые чеки неизменны.

**Уценка:** создание токенов → печать/маркировка → продажа, отмена, замена или истечение. Сканирование в корзину только проверяет токен; статус `SOLD` ставится **в той же транзакции**, которая записывает продажу, платёж и складское движение. При двух одновременных кассах блокировка токена и уникальная связь с `sale_item` допускают только одну успешную продажу. Удаление товара из корзины ничего не погашает. Возврат использует фактически оплаченную сумму и исходное распределение по партии, но **не возвращает старый токен в состояние AVAILABLE**.

Повторная печать того же активного кода не является безопасной заменой: физически могут существовать две этикетки. Для замены менеджер аннулирует старый токен и печатает новый, связанный через `replacement_for_id`. Это не делает физическое копирование невозможным, но исключает два успешных списания одного кода. Поле `printed_at` не доказывает, что принтер действительно вывел бумагу; журнал фиксирует действие приложения.

Для мутаций нужны серверные права и аудит. Вместо множества ролей на каждую кнопку V1 достаточно отдельных прав `promotions.manage` и `markdowns.manage` с проверкой в API; отдельное право на замену этикетки можно добавить, если операционно нужно. Чтение закупочной стоимости остаётся под `costs.read`. POS уже работает онлайн; при недоступном сервере одноразовый токен нельзя подтверждать локально.

## Существующие записи и переход

Нельзя просто удалить нынешние `limited_discount` продукты: на них ссылаются продажи, возвраты, движения и уже напечатанные групповые штрихкоды. Рекомендуемый переход:

1. Нормализовать категории, добавить таблицы акций/уценок и новый `PricingService`, не меняя старые чеки.
2. Перенести действующие `discount_all` в **продуктовые акции с фиксированной ценой без даты окончания**. Вернуть `products.price` к `regular_price`; затем закрыть старый путь создания `discount_all`. Миграция должна атомарно сохранить доступную цену, чтобы касса не увидела промежуточное состояние.
3. Новые уценки создавать только как уникальные `MarkdownUnit`. Существующие групповые этикетки оставить на совместимом серверном пути до продажи, истечения партии или явной перемаркировки менеджером. Помечать такие продажи как `LEGACY_MARKDOWN`; **не обещать** для них одноразовость, которой старые этикетки не имеют.
4. Для явной перемаркировки оставшегося legacy-остатка аннулировать общий код, вернуть его количество в исходный товар/партию и выпустить уникальные токены. Это отдельная атомарная операция с обязательной физической заменой этикеток; автоматом делать её нельзя.
5. Когда legacy-остаток исчезнет, удалить старый путь записи, но оставить строки и связи, необходимые историческим отчётам. Переходные отчёты должны суммировать исходный товар, legacy-варианты и новые markdown-продажи без двойного счёта.

В API продажи осталось старое поле `discountPercent`, хотя кассовый UI уже не предлагает ручную скидку. После перехода стоит закрыть или явно выделить этот legacy-путь, чтобы он не стал третьим неуправляемым источником цены.

## Проверяемые инварианты V1

- У каждого нового markdown-токена один уникальный непрозрачный штрихкод, одна физическая единица и не более одной успешной продажи.
- Создание/отмена уценки меняет логическую доступность, **не** `physical_on_hand` и не складские движения.
- Обычный штрихкод никогда не продаёт зарезервированную для уценки единицу; markdown-код списывает свою партию ровно один раз.
- Цена markdown фиксирована; процентная акция следует за обычной ценой; фиксированная акция хранит свою цену.
- Markdown имеет приоритет над акцией; несколько акций не складываются.
- Сервер пересчитывает цену при оплате; чек, стоимость партии и источник цены фиксируются навсегда.
- Возврат опирается на историческую продажу и не оживляет использованный токен.
- Код отменённой, просроченной или уже проданной этикетки не превращается в обычный скан.
- Границы магазина, права доступа, локальный часовой пояс и денежное округление проверяются на сервере.

## Порядок внедрения

1. Категории и схема акций; серверный расчёт обычной цены/акций; продуктовые и категорийные акции; снимок источника цены в продаже. Проверить расписание, динамические категории, конфликты акций, налог, отчёты и конкурентное изменение цены.
2. Схема markdown и логический резерв по партиям; выдача уникальных кодов; сканирование, корзина, атомарное погашение и возврат; печать, замена, отмена и истечение.
3. Перенести существующие скидки и legacy-этикетки по описанному выше совместимому пути; удалить двойные механизмы записи цен после проверки остатков.
4. Добавить минимальную аналитику по источнику цены, сумме скидок и валовой марже; дополнить интеграционные тесты сценариями двух касс, двух партий с разной стоимостью, завершением акции во время открытой корзины и возвратом уценённой единицы.

Это намеренно более узкая модель, чем полный «движок скидок»: в V1 действует **не более одного** источника сниженной цены на строку продажи, и он должен быть объясним по сохранённому ID акции или токена.
